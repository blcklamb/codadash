# Plan: 라이트 모드 보완

## Goal
Make the existing light-mode choice a complete, consistent light theme across the codadash web app. Done means every current route and UI state uses a readable light palette—including the fixed sidebar, navigation states, editor/code surfaces, forms, battle/result panels, overlays, dialogs, loading screen, and native controls—without dark-only colors leaking through; the selected theme remains persisted, applies without navigation, and is covered by automated checks at desktop and mobile widths.

## Scope

### In scope
- Audit and correct all theme-sensitive colors in `apps/web/src/style.css`, especially the many hard-coded dark palette values that currently bypass the light-theme variable overrides.
- Extend the semantic theme-token approach so backgrounds, text, borders, shadows, selected/hover states, controls, editor/typing surfaces, status banners, syntax colors, and overlays have intentional light and dark values.
- Cover the fixed boot/loading markup and initial paint in `apps/web/index.html`, which currently hard-codes the dark background and text before React applies `data-theme`.
- Preserve the existing persisted `Settings.theme` behavior in `apps/web/src/lib.ts` and `apps/web/src/main.tsx`; only adjust startup/theme application if needed to prevent a light-mode flash or stale browser theme color.
- Expand `tests/e2e/visual.spec.ts` to validate representative routes and states in both themes, including the existing persistence behavior and responsive overflow checks.

### Explicitly out of scope
- Changing the product's pixel-terminal visual language, layout, typography, gameplay, or server/shared contracts.
- Adding system/automatic/three-way theme selection or account synchronization.
- Replacing the stylesheet with a separate duplicated light stylesheet; the fix should follow the existing token/override pattern.
- Reworking unrelated hard-coded colors that are intentionally content-specific and remain readable in both themes after review.

## Verified understanding
- The previous theme work added `Settings.theme`, applies `document.documentElement.dataset.theme` from the settings effect, and adds a light override at the end of `style.css`; the existing e2e test only proves the setting attribute and persistence.
- The current stylesheet still contains a large number of fixed dark colors before the light override. Confirmed examples include `.sidebar` (`#101510`), navigation text/hover/selected colors, multiple form/table/battle/editor surfaces, modal/backdrop colors, and later pixel-terminal overrides such as `.code-preview` (`#141a13`), `.battle-input-wrap`, `.toggle`, `.new-best`, and syntax colors. These rules win or remain visible in light mode, explaining the report that some UI stays dark.
- The light override covers only a subset of selectors and does not cover the fixed boot screen. `apps/web/index.html` duplicates the dark boot palette inline, so a persisted light user can see a dark loading screen during startup.
- The existing e2e visual test has a theme persistence test but does not assert computed colors or inspect the full route matrix in light mode. The repository's established verification commands are `npm run check`, `npm run build`, `npm test`, and `npm run test:e2e`.
- Git history shows the immediately preceding theme feature (`20e65c4`, “feat: add persisted light and dark themes”) introduced the current token/override structure and its visual regression test; the follow-up should extend that structure rather than introduce a new theming mechanism.

## Phases

### Phase 1 — Establish complete theme tokens and startup behavior
**Changes**
- In `apps/web/src/style.css`, inventory every `background`, `background-color`, `color`, `border-color`, and `box-shadow` literal that represents the UI palette. Replace dark-only literals with semantic variables where the value is theme-dependent, adding narrowly named variables for any distinct surface/state that cannot share `--bg`, `--panel`, `--surface`, `--surface-raised`, `--line`, `--text`, `--muted`, `--shadow`, `--mint`, `--purple`, `--error`, or `--yellow`.
- Keep the existing dark values as the default token values, so dark mode remains the compatibility baseline. Define deliberate light values for each token in `:root[data-theme='light']`; do not rely on opacity over an unknown background for text or panels.
- Update all affected selectors—including sidebar/topbar/navigation, forms and inputs, records tables, battle/lobby/result UI, editor/typing/code preview, toggle/segmented controls, toast/notice/dialog/backdrop, status cards, hover/focus states, and the late pixel-terminal overrides—to consume the tokens. Preserve syntax/status meaning while choosing light-background contrast.
- In `apps/web/index.html`, make the inline boot screen use the theme tokens or equivalent light/dark startup rules. If the persisted settings value can be read safely before React mounts, set the root theme before first paint; otherwise ensure the boot screen itself adapts immediately and does not show a dark-only screen for a saved light preference. Keep the existing dark fallback for missing or malformed storage.
- In `apps/web/src/main.tsx`, retain the current authoritative settings effect and update only the document-level startup metadata/theme color if needed so it tracks the selected palette without changing navigation or persistence semantics.

**Tests and verification**
- Run a stylesheet color audit (search for remaining fixed palette literals and review each intentional exception).
- Run `npm run check` and `npm run build`.
- Manually or with Playwright inspect computed `backgroundColor`, `color`, and `borderColor` for the sidebar, selected nav item, editor, code preview, form controls, battle/result panels, dialog, and boot screen in both themes.

### Phase 2 — Add regression coverage for complete light-mode rendering
**Changes**
- Extend `tests/e2e/visual.spec.ts` using stable accessible selectors and existing local-storage initialization. Keep the current persistence assertions, then exercise both `light` and `dark` explicitly.
- For the existing route matrix (`/`, `/daily`, `/battle`, `/records`, `/settings`) at desktop and mobile widths, assert the root theme and that representative visible surfaces resolve to light/dark-appropriate computed colors rather than the old dark literals. Include the sidebar/navigation and at least one content/editor surface so a partial override cannot pass.
- Add a startup/boot assertion if the test harness can observe it reliably; otherwise cover the persisted light reload immediately after navigation and ensure no route requires a manual refresh or theme re-selection.
- Preserve the existing horizontal-overflow and screenshot checks. Use screenshots as review artifacts, not brittle pixel snapshots, unless the repository's current Playwright configuration already supports stable snapshot baselines.

**Tests and verification**
- Run the focused visual suite: `npx playwright test tests/e2e/visual.spec.ts`.
- Inspect generated desktop/mobile screenshots for all routes in light mode and confirm readable text, visible borders/focus states, and no dark panels left behind.
- Run `npm test` and `npm run test:e2e`.

### Phase 3 — Final production verification
**Changes**
- Reconcile any contrast or selector gaps found during the route/state review without changing the public settings contract.
- Remove dead theme overrides made unnecessary by tokenization and keep the stylesheet ordering clear: base/default tokens, component rules, then only the small theme-specific variable/state exceptions required.

**Tests and verification**
- Run `npm run check`.
- Run `npm run build`.
- Run `npm test`.
- Run `npm run test:e2e`.
- Confirm the final diff is limited to the web theme implementation, startup markup if needed, and focused regression coverage.

## Risks
- The stylesheet is large and has late overrides; fixing only the first matching rule may leave later pixel-terminal rules dark. Audit from top to bottom and test computed styles, not only source tokens.
- Native `select`, `input`, `dialog`, and backdrop rendering can retain dark browser styling; keep `color-scheme` synchronized and explicitly style controls where necessary.
- Syntax highlighting, error overlays, success/new-record banners, and battle status colors may become low-contrast on white backgrounds; verify each semantic state in light mode.
- The persisted settings object may predate `theme`; malformed or missing storage must still fall back to dark without blocking startup.
- Applying a theme only in React can cause a dark flash for a saved light preference; verify initial boot behavior separately from post-mount behavior.
- Visual assertions based on exact RGB values can be brittle if the palette is refined; prefer semantic relationships and a small set of stable computed-color checks.

## Assumptions
- The report refers to the existing local light theme, not a request for a new theme design; the goal is complete coverage of the current application.
- Dark mode is the compatibility baseline and remains the default for new users and legacy settings records.
- Theme remains a local preference using the existing `keybit.settings` storage contract; no server migration or account sync is required.
- The simplest supported implementation is semantic CSS tokens plus targeted theme state rules, not duplicated light/dark component stylesheets. A wholesale rewrite of all colors was considered and rejected because it increases visual drift risk; only theme-dependent palette literals will be tokenized.
- A startup root attribute/script is allowed if needed to prevent a persisted-light flash, but React's existing settings effect remains the source of truth after initialization.
- The current route matrix and Playwright setup are the appropriate regression surface; screenshot inspection is preferred over introducing new snapshot infrastructure.
- Any remaining fixed color must be documented by its semantic purpose in the implementation review (for example, a syntax/status accent) and verified for contrast in both themes.

## Open questions
- None. The required behavior and implementation choices are answerable from the current code and existing theme feature history.

## Acceptance criteria
- Selecting light mode changes the complete visible application—not only selected panels—and persists after reload.
- No known dark-only sidebar, navigation, editor, form, battle/result, overlay, dialog, or loading-screen colors remain visible in light mode.
- Both themes retain readable text, borders, controls, status colors, focus indicators, and syntax highlighting across desktop and mobile routes.
- `npm run check`, `npm run build`, `npm test`, and `npm run test:e2e` pass.
- The regression suite proves both immediate theme application and persistence without relying on implementation-specific class selectors.
